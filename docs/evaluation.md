# 评测说明

指标不写在文档里，而是由脚本现场测量：`scripts/evaluate.py` 会跑实验、打印表格并把原始结果 JSON 落盘到 `reports/`。

```bash
python scripts/evaluate.py          # 离线：假 LLM，不产生 API 费用
python scripts/evaluate.py --live   # 追加：真实 LLM 的待办抽取质量
```

## 一、指标定义

### 1. 并行编排收益

| 项 | 定义 |
|----|------|
| 并行耗时 | LangGraph Fan-out 端到端耗时（`run_meeting_pipeline`），重复 3 次取中位数 |
| 串行基线 | 同样的三个 Agent、同样的假 LLM 延迟，顺序 `await` 三者耗时 |
| 加速比 | 串行耗时 / 并行耗时 |
| 编排固有开销 | 并行耗时 − 单次模拟 LLM 延迟（含状态合并、调度、报告落盘） |

用假 LLM 注入固定延迟（默认 0.4s/次），是为了把「编排带来的差异」从「模型响应波动」里隔离出来 —— 真实 LLM 延迟抖动大，测出的加速比不可比。

### 2. 降级可靠性

把 LLM 打成必失败，重复 3 次，统计：

- **完成率**：Pipeline 是否仍返回 `completed`；
- **错误可观测率**：`errors` 是否如实记录了三个并行 Agent 的失败；
- **报告写出率**：报告文件是否仍然落盘且非空。

### 3. 报告完整率

报告中「会议纪要 / 待办事项 / 会议洞察」三节非空且不含占位符（如 `*（摘要生成失败）*`）的比例。

### 4. 待办抽取质量

在人工标注集 `tests/fixtures/golden_actions.json` 上做二部匹配：

- 命中条件：负责人匹配（双向包含即算）**且**任务描述命中该条目任一关键词；
- 输出 precision / recall / F1，以及「截止时间填充率」（抽取结果里带合法 `YYYY-MM-DD` 的比例）。

`--live` 用真实 LLM；不加参数时用假 LLM，只验证评分链路本身（输出里会明确标注为「fixture 自检」，不代表模型能力）。

## 二、最近一次结果

环境：Windows 11 / Python 3.12.8 / 假 LLM 延迟 0.4s × 3 次调用

| 指标 | 数值 |
|------|------|
| 并行编排中位耗时 | 0.421s |
| 串行基线中位耗时 | 1.222s |
| 编排加速比 | 2.9x |
| 并行编排固有开销 | 0.021s |
| 降级完成率 | 3/3 |
| 错误可观测率 | 3/3 |
| 报告完整率 | 100% |
| 待办抽取 P/R/F1（live, abab6.5s-chat） | 1.00 / 1.00 / 1.00（3 条标注） |
| 待办截止时间填充率（live） | 100% |

## 三、口径与限制

- **抽取样本太小**：标注集只有 3 条待办，只能证明「抽取链路 + 评分链路可用」，不能作为模型准确率结论。要作为指标使用，需要扩到几十条并覆盖多说话人、隐式任务、跨句指代等难例。
- **加速比随模型延迟变化**：并行收益来自「三条链路延迟重叠」，模型越慢、收益越大；0.4s 的模拟延迟只是为了构造可复现的对照。
- **没有真实音频的端到端指标**：转写准确率、说话人分离准确率需要音频数据集，当前仓库不包含音频，因此不做任何转写准确率声明。
- **报告完整率是结构指标**，不评价纪要内容是否忠实于原文；内容质量目前靠人工抽查。
- **降级实验用的是假 LLM**，验证的是「编排层的失败处理」而不是「真实 API 的错误码覆盖」。

## 五、RAG 检索评测（`scripts/evaluate_rag.py`）

### 1. 指标定义

| 指标 | 定义 |
|------|------|
| Recall@1 / Recall@5 | 标注的期望来源是否出现在 Top-1 / Top-5（来源 = 文档，不要求命中具体片段） |
| MRR | 正确来源排名的倒数均值 |
| 术语命中率 | 术语类问题的期望术语是否出现在检索上下文里 |
| 引用可核验率 | 返回的引用能否在索引里定位到真实 chunk（防幻觉硬指标） |
| 术语层增益 | 同一套问题在「术语层开 / 关」两组下的指标差值 |

标注集：`tests/fixtures/rag_qa.jsonl`，24 条（术语类 8 / 会议历史类 8 / 制度规范类 8）。

### 2. 最近一次结果（bge-small-zh + BM25 + 确定性精排）

| 指标 | 术语层 开 | 术语层 关 | 差值 |
|------|-----------|-----------|------|
| Recall@1 | 0.875 | 0.875 | +0.000 |
| Recall@5 | 1.000 | 1.000 | +0.000 |
| MRR | 0.938 | 0.925 | +0.013 |
| 引用可核验率 | 1.000 | 1.000 | — |

分类别（术语层开启）：术语类 0.875 / 会议历史类 0.875 / 制度规范类 0.875（Recall@1），三类 Recall@5 均为 1.000。

**消融：术语层在不同检索通道下的增益**

| 检索配置 | Recall@1 增益 | MRR 增益 |
|----------|---------------|----------|
| hybrid（向量 + BM25） | +0.000 | +0.013 |
| bm25-only | +0.042 | +0.034 |
| vector-only | −0.041 | +0.000 |

**语义通道缺失时（离线哈希向量，无模型部署 / 降级路径）**

| 检索配置 | Recall@1 增益 | Recall@5 增益 | MRR 增益 |
|----------|---------------|---------------|----------|
| hybrid | **+0.041** | +0.000 | +0.027 |
| bm25-only | +0.000 | +0.000 | +0.006 |
| vector-only | **+0.084** | +0.042 | +0.045 |

**答案级（真实 LLM，各 8 条）**

| 指标 | 术语层 开 | 术语层 关 |
|------|-----------|-----------|
| 引用可核验率 | 1.000 | 0.875 |
| 术语覆盖率（答案使用公司标准术语） | 0.625 | 0.500 |

### 3. 负结果与原因（这部分比曲线更重要）

**术语层在语义通道存在时几乎没有检索增益（+0.000 Recall@1，MRR +0.013）。** 原因是：BGE 中文小模型本身就能把「QoE」和「用户体验质量」映射到相近的语义空间，而且这些问题里还带着「验收标准」「接入频率」这类与目标文档直接匹配的内容词——缩写鸿沟本来就不构成瓶颈，扩展词反而偶尔把正确文档挤后一位。

**它在语义通道缺失时才显出价值**：换成离线哈希向量（无语义能力）后，术语扩展让 hybrid 的 Recall@1 +4.1pt、vector-only +8.4pt。也就是说，**术语表是「没有向量模型」或「向量模型弱」时的补偿手段，不是万能增益**。

**第一版还把排序做坏了（Recall@1 0.417 → 修复后 0.875）。** 两处设计错误，都是实测暴露出来的：

| 问题 | 现象 | 修复 |
|------|------|------|
| 把原查询与扩展词拼成一个查询去检索 | 扩展词稀释了原查询的语义中心，Recall@1 0.625 → 0.417 | 拆成四路独立召回 + RRF 融合（向量通道永远用原查询） |
| 术语表 chunk 靠术语密度抢占首位 | 问「QoE 验收标准」时返回术语定义而非需求文档 | 术语表只在「查询本身含术语」时参与竞争，否则降权 0.6 |
| 只按 RRF 排名融合，无法区分「谁真的回答了问题」 | 同主题文档互相抢位（policy 类 Recall@1 仅 0.125） | 增加确定性精排：查询词覆盖度 + 连续短语命中 + 小节标题命中 |

### 4. 口径与限制

- **语料是构造的示例数据**（`data/knowledge`、`data/meetings`），换真实内部文档后必须重跑，数字不能直接引用；
- **标注集 24 条**，术语类只有 8 条，A/B 差值在 ±1 条题目就会抖动，只适合看方向；
- **来源级判定**（不是片段级）：Recall 只要求命中文档，不要求命中该文档里正确的那一节；
- **答案级评测样本 8 条**且用同一套 prompt，术语覆盖率差异（0.625 vs 0.500）在统计上并不显著；
- **精排是确定性特征**，非 Cross-Encoder reranker；换成 bge-reranker 预计还能提升，但会引入模型体积与推理延迟。

### 5. 回归建议

把评测接到改动流程里：

```bash
python -m pytest                # 功能与不变式
python scripts/evaluate.py      # 编排收益与降级行为是否退化
python scripts/evaluate_rag.py  # 检索 Recall@K / MRR / 术语消融是否退化
```

`reports/evaluation-*.json` 与 `reports/rag-eval-*.json` 保留了每次运行的全部原始数字（含逐题明细），便于对比改动前后的差异。
