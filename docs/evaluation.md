# 评测说明

指标不写在文档里，而是由脚本现场测量：`scripts/evaluate.py` 会跑实验、打印表格并把原始结果 JSON 落盘到 `reports/`。

```bash
python scripts/evaluate.py          # 离线：假 LLM，不产生 API 费用
python scripts/evaluate.py --live   # 追加：真实 LLM 的待办抽取质量
```

## 一、指标定义

### 1. 并行编排收益

| 项 | 定义 |
|----|------|
| 并行耗时 | LangGraph Fan-out 端到端耗时（`run_meeting_pipeline`），重复 3 次取中位数 |
| 串行基线 | 同样的三个 Agent、同样的假 LLM 延迟，顺序 `await` 三者耗时 |
| 加速比 | 串行耗时 / 并行耗时 |
| 编排固有开销 | 并行耗时 − 单次模拟 LLM 延迟（含状态合并、调度、报告落盘） |

用假 LLM 注入固定延迟（默认 0.4s/次），是为了把「编排带来的差异」从「模型响应波动」里隔离出来 —— 真实 LLM 延迟抖动大，测出的加速比不可比。

### 2. 降级可靠性

把 LLM 打成必失败，重复 3 次，统计：

- **完成率**：Pipeline 是否仍返回 `completed`；
- **错误可观测率**：`errors` 是否如实记录了三个并行 Agent 的失败；
- **报告写出率**：报告文件是否仍然落盘且非空。

### 3. 报告完整率

报告中「会议纪要 / 待办事项 / 会议洞察」三节非空且不含占位符（如 `*（摘要生成失败）*`）的比例。

### 4. 待办抽取质量

在人工标注集 `tests/fixtures/golden_actions.json` 上做二部匹配：

- 命中条件：负责人匹配（双向包含即算）**且**任务描述命中该条目任一关键词；
- 输出 precision / recall / F1，以及「截止时间填充率」（抽取结果里带合法 `YYYY-MM-DD` 的比例）。

`--live` 用真实 LLM；不加参数时用假 LLM，只验证评分链路本身（输出里会明确标注为「fixture 自检」，不代表模型能力）。

## 二、最近一次结果

环境：Windows 11 / Python 3.12.8 / 假 LLM 延迟 0.4s × 3 次调用

| 指标 | 数值 |
|------|------|
| 并行编排中位耗时 | 0.421s |
| 串行基线中位耗时 | 1.222s |
| 编排加速比 | 2.9x |
| 并行编排固有开销 | 0.021s |
| 降级完成率 | 3/3 |
| 错误可观测率 | 3/3 |
| 报告完整率 | 100% |
| 待办抽取 P/R/F1（live, abab6.5s-chat） | 1.00 / 1.00 / 1.00（3 条标注） |
| 待办截止时间填充率（live） | 100% |

## 三、口径与限制

- **抽取样本太小**：标注集只有 3 条待办，只能证明「抽取链路 + 评分链路可用」，不能作为模型准确率结论。要作为指标使用，需要扩到几十条并覆盖多说话人、隐式任务、跨句指代等难例。
- **加速比随模型延迟变化**：并行收益来自「三条链路延迟重叠」，模型越慢、收益越大；0.4s 的模拟延迟只是为了构造可复现的对照。
- **没有真实音频的端到端指标**：转写准确率、说话人分离准确率需要音频数据集，当前仓库不包含音频，因此不做任何转写准确率声明。
- **报告完整率是结构指标**，不评价纪要内容是否忠实于原文；内容质量目前靠人工抽查。
- **降级实验用的是假 LLM**，验证的是「编排层的失败处理」而不是「真实 API 的错误码覆盖」。

## 四、回归建议

把评测接到改动流程里：

```bash
python -m pytest                # 功能与不变式
python scripts/evaluate.py      # 编排收益与降级行为是否退化
```

`reports/evaluation-*.json` 保留了每次运行的全部原始数字，便于对比改动前后的差异。
